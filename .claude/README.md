# `.claude/`

**Session configuration, not project content.** What Claude Code loads when a session starts here.

| Path | What it is |
|---|---|
| `settings.json` | Tracked. Two things and nothing else: the enabled plugins and the hook registrations, each with a `statusMessage` and an explicit `timeout` sized to the hook. |
| `settings.local.json` | Untracked (`.gitignore`). Machine-specific permissions: the allow-list that pre-empts the permission classifier on command shapes it cannot resolve. Never a hook, never a plugin. |
| `skills/<name>/SKILL.md` | Skills a session can invoke. Each opens, on the first line after its frontmatter, with the line `CLAUDE.md` § Standing rules for prompts and gates requires. No skill is judged too small to carry it, and `check:prompts` refuses one that does not, and one over its word budget in `tools/policy/prompt-budgets.json`. A skill adapted from another project's text keeps that project's license beside it, as `explore/LICENSE` keeps OpenSpec's (`docs/decisions.md` § D-30). |
| `agents/<name>.md` | Agent definitions Claude Code can spawn, under the same opening line, a word budget of their own and the same gate. `fan-out-work.md` is the exception: the session runs it as itself, never spawned. A workflow's `agentType` is resolved from the agents of the checkout its calling session started in, so a new agent is usable by a workflow once it is on the branch that session starts from. `test-builder.md` is `build-change-task.js`'s test-builder, given no tool but its structured output, which `workflows:selftest` holds. `prompt-case-author.md` writes a candidate decision case for `author-prompt-cases.js`, and `prompt-case-answerer.md` answers one for it and for `review-prompts.js`. Each is held the same way to Read and its structured output, to read the one file its workflow wrote, and can run no command or search for a case's expected answer. `branch-reviewer.md` reviews a branch before its push, from the brief `scripts/pr-review.mjs brief --local` writes, with no tool but Read, Grep and Glob; `open-pr` § 5 runs it. It is the one review of correctness and maintainability, and the rubric's home since `docs/decisions.md` § D-37 retired `pr-reviewer.md` to `docs/retired/`. |
| `workflows/<name>.js` | Workflow scripts a skill or an agent runs through the Workflow tool, each named for what it does, with its header naming what runs it. `build-change-task.js` builds and reviews one task of a product change (`change-build` step 3), with the sizes `tools/policy/agent-workflows.json` gives it. It stops as `not-red`, before any review, a task of a kind that file names when a scenario the parent named has neither a red record nor an already-green report. For a kind the policy gives independent tests, the `test-builder` agent, whose only tool is its structured output, writes them beside the build. After the review, the architect's runs, of those tests and of every build-stage test an earlier task committed, route each failure to a rewrite, a fix or a re-design, the fixer told only the four fields. `verify-change-trace.js` takes a change's scenario trace (`change-verify` step 4): one tracer per group of scenarios, judging only whether the tests the traceability record gives each scenario exercise it, the design lenses the session names, and skeptics for each gap, sized by `tools/policy/agent-workflows.json`, each row's result read in code from the fresh run `scripts/fresh-run.mjs` wrote, its result written out by `scripts/render-trace.mjs`. Its clause run takes the answers `scripts/judge-trace-clauses.mjs` writes outside it, and sends a row whose tests may not assert a clause to the skeptics, running no tracer. `review-prompts.js` runs one agent per prompt file in a batched prompt review, each in a worktree of its own, on the findings that met the threshold `tools/policy/agent-workflows.json` gives, and has skeptics judge each edit and each consolidation of a prompt that an edit would take past its word budget. It answers each stored decision case of a file an upheld branch changes with its old text and its new, returning a prose case's answers for `scripts/grade-prose-cases.mjs`, which grades them outside it and keeps no branch out, and says which branches the `continuous-prompt-improvement` agent may merge, which group branches it removes, merged or not, which analyses it may mark read and which findings it holds (`CLAUDE.md` § Prompt reviews). It holds out of those it removes a branch a report names that no file agent of the run could have been given, and refuses a report whose branch holds a character outside `A-Za-z0-9._/-`, or whose consolidation names no commit hash, since each is pasted into a command. Each finding comes with its `match`, the answer of `scripts/match-held-findings.mjs`, run before it, that decided its key, the model's or the session's, and it refuses one the key or the count does not bear out. `author-prompt-cases.js` writes candidate cases for that review's settled findings, one author per lens, and validates the ones it chooses against the trunk's text before any edit exists, or against a branch's head where that branch adds the rule a case tests (`args.ref`). `check:prompts` holds the words of each one's string literals, where its agents' prompts are, to a budget in `tools/policy/prompt-budgets.json`, but asks no opening line of it: each opens with the `meta` literal the runtime needs first, with its header right after. `workflows:selftest` runs each against stubbed agents. |
| `prompt-cases/` | The stored decision cases a prompt review answers each prompt it changes with, one JSON file each, with a `README.md` that gives their format and how one is written, validated and judged (`docs/decisions.md` § D-32), a prose case's included (`docs/decisions/asdlc-openspec-1kie.md` § Decision). Not loaded at session start: the prompt reviewer reads them and passes them to the two workflows above, a prose case to the review alone. |
| `worktree-CONTEXT.md.tmpl` | The briefing `scripts/render-worktree-context.mjs` renders into a new worktree as `.worktree/CONTEXT.md`, which `CLAUDE.md` imports. `check:prompts` holds it to a word budget in `tools/policy/prompt-budgets.json`. |
| `worktrees/` | Where Claude Code provisions worktrees. Gitignored; the rule is load-bearing (see `.gitignore`). |

## The hooks

Every hook is a Node script under `scripts/hooks/`, registered in `settings.json`, and can be run by
hand with `node scripts/hooks/<name>.mjs < /dev/null` because the shared stdin reader returns null on
empty input.

**A registration names its script as `node "$CLAUDE_PROJECT_DIR"/scripts/hooks/<name>.mjs`, never
by a relative path.** Claude Code runs a hook in the session's current directory, so a relative path
stops loading after a Bash `cd`, and a guard that fails to load blocks nothing
(`asdlc-openspec-7dj`). `worktree:selftest` loads every registration from a subdirectory and from
outside the checkout. `CLAUDE_PROJECT_DIR` names the directory the session started in and does not
follow it into a worktree, so a session that has entered one runs the primary checkout's copy of
each hook, as current as that checkout's last pull. A hook that must act on the worktree finds it
from the payload: one that acts on the session's directory from its `cwd`, as `gate-summary.mjs`
and `guard-git.mjs` do, and one that acts on an edited file from that file's own path
(`editedCheckout` in `scripts/hooks/_shared.mjs`), as `block-generated-edit.mjs` does, since a
session in a worktree can edit the primary checkout's files too. A hook that read
`CLAUDE_PROJECT_DIR` for it would judge the primary checkout instead, which is how the guard applied
no git rule in any entered worktree until `asdlc-openspec-bvf`.

| Event | Script | Blocks? | What it does |
|---|---|---|---|
| `PreToolUse` on Bash | `guard-git.mjs` | yes; its git rules in a linked worktree only, but for `git worktree prune` | Tokenises the command; refuses pushes, checkouts, branch writes and merges against the protected branches, and `git worktree`, `gc` and `prune`, from a worktree; and every git command in a directory under `.claude/worktrees/<name>/` where git answers for another checkout, as it does in what a removed worktree leaves. From any checkout, it refuses a `git worktree prune` that is not a dry run, which in a dev container takes every host worktree's record. From any checkout, refuses a `gh pr create` that does not name `main` as its base, a `gh pr review --approve`, the person's gate on a head on the high-risk floor (`docs/decisions.md` § D-57), a `gh pr merge --admin`, which merges past the checks the trunk's ruleset requires (`docs/decisions.md` § D-47), and graphify's `update`, `watch`, `hook install` and `claude install`, which erode the local code graph or write graphify's advice to run `update` into `CLAUDE.md` (`docs/decisions.md` § D-20). Fails closed in a worktree when it cannot read its input. |
| `PreToolUse` on Bash | `guard-unprovisioned-worktree.mjs` | yes, in a linked worktree not on an `agent/*` branch | Refuses every command in a worktree `scripts/new-worktree.sh` did not provision: one on a `worktree-<name>` branch, which `EnterWorktree`'s native fallback cuts with no briefing. A file of its own, off the high-risk floor that holds `guard-git.mjs` (`docs/decisions.md` § D-58), though its word budget is on it (`docs/decisions.md` § D-59). |
| `PreToolUse` on Write and Edit | `block-generated-edit.mjs` | yes | Refuses an edit to generated output and names where the change belongs. It finds the checkout from the edited file's own path, not the payload's `cwd`, so it refuses the edit in a worktree as in the primary checkout. |
| `PreToolUse` on Write and Edit | `guard-workflow-edit.mjs` | yes, on a workflow | Refuses an edit that would let a workflow other than `pr-review.yml` approve a pull request or pass the required `verify` check: a `pull-requests: write`, `statuses: write`, `checks: write` or `write-all` grant, or, outside `verify.yml`, a job named for the check (`docs/decisions.md` § D-57); and one that would let a workflow but the prompt review's read the agents' App key, or the prompt review's read it on another event or outside its environment (`docs/decisions/asdlc-openspec-ic9h.md` § Decision). It finds the checkout as the edit hook above does. |
| `Stop` and `SubagentStop` | `gate-summary.mjs` | never | Runs the fastest gates concurrently over the checkout the stopping agent worked in, untracked files included, and prints one verdict line into the transcript; a subagent's verdict says it is one. It never denies the stop: a hook people disable is a lie in version control. |
| `WorktreeCreate` | `worktree-create.mjs` | yes | Provisions through `scripts/new-worktree.sh`: `agent/<name>` cut from `origin/main`, with a rendered briefing, never Claude Code's native fallback off the default branch. |
| `WorktreeRemove` | `worktree-remove.mjs` | no | Removes the checkout, keeps the branch, and runs the branch sweep for paths under `.claude/worktrees/` only. It prunes no record itself, and for any other path touches none. |

**A running session picks up a hook added to the settings file it loaded, with no restart.** A
hook added to it mid-session fired on the session's next matching tool call, in a headless session
and an interactive one, and a `WorktreeCreate` hook added mid-session took over `EnterWorktree`
(verified against the CLI, 2.1.294, `asdlc-openspec-gm86`). Claude Code's hooks documentation
(https://code.claude.com/docs/en/hooks) says such an edit is "normally" picked up, so a session
that still behaves as it did before an edit is the one to restart. The hook budget is a few hundred
milliseconds: an in-session hook may be unsound (a cached lint is) but must be fast, and a slower
tier of the gate ladder never trusts a faster one.
